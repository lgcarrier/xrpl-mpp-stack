# Changelog

All notable changes to the Open XRPL MPP Stack are documented here.

## Unreleased

### Testnet tooling

- Added `python -m devtools.rlusd_fund`, a browser-free XRPL Testnet workflow
  that creates or reuses a private wallet, funds XRP, establishes the official
  RLUSD trust line, and acquires an exact target balance with spend, fee,
  finality, and crash-safe reconciliation controls. The session-token
  `rlusd_topup` helper remains available as a legacy fallback.
- Corrected the built-in Testnet RLUSD issuer to Ripple's current `rQhWct...`
  account, retained the former `rnEVY...` account as an explicit legacy
  constant, and reject that former issuer when it is configured as RLUSD.

### Release automation

- Hardened TestPyPI and PyPI post-publish verification against stale Simple
  API caches by disabling pip's shared cache and extending the bounded retry
  delay to ten minutes.

## Stack 0.2.0 - 2026-09-03

- Replaced the repository's pre-standard wire format with the current MPP HTTP
  authentication contract, including RFC 8785 canonical JSON, strict base64url
  encodings, multiple challenges, `Accept-Payment`, and challenge-selected
  `Payment-Authorization`.
- Added the Ripple-compatible XRPL `charge` profile with named networks,
  canonical XRP/issued-currency/MPT descriptors, transaction-blob and
  transaction-hash credentials, XRPL DID sources, invoice binding, exact
  transaction validation, and pull/push settlement.
- Hardened buyer signing with HTTPS-only RPC defaults, a final autofilled fee
  ceiling, explicit source-capped IOU pathfinding/slippage, exact charge-receipt
  hash binding, and deterministic nonzero PaymentChannel-open claims.
- Replaced reusable prepaid session credentials with XRPL Payment Channel
  `open`, cumulative `voucher`, and `close` credentials backed by atomic
  high-water state and single-use challenge claims.
- Added a KMS/HSM-friendly recipient signing boundary, local-seed adapter,
  Redis-leased background claim redemption and idle session finalization, plus
  an opt-in live Testnet PayChannel open/voucher/close/redemption round trip.
- Bound charge replay retention to the authenticated challenge lifetime plus
  ledger validation and clock-skew margins, and made ambiguous settlement a
  non-cacheable `503` reconciliation state instead of a new-payment prompt.
- Added draft-01 OpenAPI payment discovery for `charge` and `session` offers.
- Added the standalone `xrpl-mpp-mcp` package for native MPP metadata,
  capability advertisement, paid-operation binding, replay-safe processing,
  and exact MCP payment error codes.
- Added opt-in typed lifecycle hooks and a sanitized HTTPS payment-outcome
  relay. Both are explicitly non-normative application features.
- Added official `mpp-tools` core/HTTP conformance coverage and CI wiring.
- Added a package-driven MCP gate that loads the pinned mpp-tools
  `json_rpc_mcp_payment` fixture without misclassifying the runner-owned flow
  as adapter conformance, plus deterministic charge/session golden fixtures
  generated by Ripple's XRPL MPP SDK at commit
  `6907484c92d217da406e2f3d7b5e6587703c6ea8`.
- Upgraded to `xrpl-py` 5.x and added explicit RFC 8785 support.
- Reworked public documentation, examples, configuration, packaging, and tests
  around the clean-break 0.2 contract.
- Added fail-closed publish gates for the full local suite, docs, container,
  and pinned conformance workflow, and moved wheel licenses into each
  distribution's PEP 639 metadata directory.
- Aligned all six build backends on Hatchling 1.32 with Twine 7 metadata 2.5
  validation while retaining a `<1.33` upper bound.

### Breaking changes

- Removed the pre-0.2 Python compatibility surface: legacy asset/amount models
  and identifier helpers, facilitator `verify_payment` / `settle_payment`, the
  client challenge selector's `asset` alias, payer asset resolution, and the
  receipt-record `asset_identifier` / `tx_hash` aliases.
- Network values are now `mainnet`, `testnet`, and `devnet`; CAIP-like
  `xrpl:0` / `xrpl:1` values are rejected.
- Currency values are now `XRP` or canonical XRPL JSON descriptors;
  `XRP:native` and `CODE:issuer` are rejected on the 0.2 wire.
- The former session token, request-usage, balance, and application-level
  refill fields have been removed. Session proofs are signed cumulative
  PaymentChannel claims.
- The selected credential header can be `Payment-Authorization`, allowing an
  existing bearer `Authorization` header to remain intact.
- Receipt consumers must rely on the four required core fields and treat XRPL
  settlement fields as method extensions.
- The generic upstream subscription intent does not imply XRPL subscription
  support; no XRPL subscription profile is implemented.
